## Corrected contract and persistence mappings

| Capability | Persistence and invariants |
|---|---|
| IDs | Positive JSON integer/int64, SQL BIGINT for every entity and FK identifier |
| Baseline | `veterinary_examination` with BASELINE and NULL case; `weight_record` context BASELINE; `horse.health_status`; atomic write; filtered baseline uniqueness returns 409 |
| Weight | `weightKg` → `weight_record.weight` DECIMAL(6,2); `recordedAt` → `measured_at`; JWT actor → `recorded_by_user_id`; deterministic descending history |
| Health update | Optional `healthStatus` on Veterinarian examinations and re-examinations atomically sets `horse.health_status` plus exam `health_status_set`; FIT/MONITORING/INJURED/QUARANTINED; no new health table or competing availability field |
| Incident | `incident`: type OFF_FEED/COLIC_SIGNS/FEVER/HOOF_OR_LEG_PROBLEM/OTHER; observed severity LOW/MEDIUM/HIGH; status REPORTED→UNDER_REVIEW→RESOLVED, with direct REPORTED→RESOLVED allowed; optional source FKs, at most one; unique non-NULL pre-check FK; server code/actor/report timestamp. OPEN_CASE and LINK_CASE require REPORTED/unlinked and move to UNDER_REVIEW; RESOLVE is terminal, preserves the case link and never closes the case; invalid/repeated review returns 409. |
| Case | `medical_case`: OPEN/CLOSED; POST `/api/medical/cases` accepts only `horseId` and `reason`, creates an independent OPEN case and does not link an Incident. `reason` → `condition_summary`. Incident linkage through OPEN_CASE/LINK_CASE in POST `/api/incidents/{incidentId}/review` writes `incident.medical_case_id`; no `medical_case.incident_id` column exists. Vet closes only an OPEN case with at least one clinical exam; Injury or TreatmentPlan additionally requires the latest RE_EXAMINATION to be RECOVERED. Treatment tasks must be completed, directly linked restrictions lifted and linked incidents resolved. Closure sets server timestamp and never performs those actions implicitly. |
| Exam | `veterinary_examination`: EXAMINATION/RE_EXAMINATION require same-horse case; symptoms/findings map `findings`; nullable diagnosis; clinical severity MILD/MODERATE/SEVERE; re-exam outcome NOT_RECOVERED/IMPROVING/RECOVERED |
| Injury | `injury`: required region/severity/recovery; optional same-case exam; region NVARCHAR(100), side NVARCHAR(20), opaque position_3d VARCHAR(100); no invented coordinates table or clinical_notes column |
| Treatment | Single `treatment_plan` per case; medication instructions NVARCHAR(MAX), rest_period NVARCHAR(100), care_instructions NVARCHAR(2000), re_examination_date DATE; no fictional plan status |
| Groom work | `care_task` with treatment_plan_id only (XOR source rule), plus approved `assigned_groom_user_id BIGINT NULL` FK to `app_user(id)`; Vet supplies `assignedGroomUserId` and service validates active GROOM role for every treatment task. Only that Groom may list/complete; `completed_by_user_id` comes from JWT. PENDING/COMPLETED derives from paired completion columns. The approved column has **not** been migrated by CORE-006. |
| Restriction | `medical_restriction`: LIMITED/LOCKED; effectiveAt later than server now returns 400 VALIDATION_ERROR (Leader Option A), so accepted restrictions apply immediately. Active slot = lifted_at IS NULL; unique active-per-horse index; competing creation returns 409, including races; review_date is not an expiry; no AVAILABLE row or future scheduler. |
| Exercise rules | PUT `/api/medical/restrictions/{restrictionId}/exercise-rules`; replace set atomically; each rule has exactly one `exerciseId` or `exerciseTypeNote` pattern, even though the existing SQL CHECK accepts both. LOCKED blocks all; LIMITED evaluates matching PROHIBITED first, then requires an ALLOWED match if any ALLOWED rules exist; with no ALLOWED rules it allows unless prohibited. |
| Availability | GET `/api/horses/{horseId}/training-availability`; no unlifted row → AVAILABLE, otherwise LIMITED/LOCKED; no extra horse availability field |
| Thresholds | CORE-019 owns global managed-config GET, effective horse GET, Vet PUT and END, and horse override resolution; CORE-030 consumes the effective value. Horse override maps `horse_threshold_override` metric/critical_value/reason/effective interval; explicit END uses `effective_to`. No global table. 180 bpm is demo/default seed only; no `WARNING = critical - 10` rule. |
| Herd health | Retained Veterinarian-only GET `/api/medical/herd-health`; counts from health_status with NULL counted separately as unassessed |
| Errors | Exact shared success/error conventions; code/message/details, no fieldErrors; 400/401/403/404/409 on all operations; business conflicts use 409, no unsupported 422 |

Required restriction capabilities remain: training availability GET, horse restriction POST, explicit lift POST, exercise rules PUT, club restrictions GET. Restriction writers and clinical writers are VETERINARIAN only. The only other writes are authorized explicit Incident reporting and scoped Groom completion. Owner summaries remain in CORE-004 `/api/owner/horses/**`, never clinical endpoints.

Case list/detail use role-selected clinical versus summary schemas. Training-facing restriction/availability reasons must contain operational explanations only. Groom work-list and completion responses use their own strict projection: task/horse/assigned Groom identifiers, operational instruction/date/slot, derived status and completion timestamp. They do not contain case diagnoses, prescriptions, the full TreatmentPlan or clinical histories. Backend assignment scoping applies before loading/mutating rows, including list pagination/counts. JWT claims supply completion actors; request bodies never accept `completedByUserId`.
